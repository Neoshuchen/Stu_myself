# AI 辅助 Markdown 学习路线生成规划

> 文档状态：后续方案，暂不开发；已按 2026-08-28 的全局 AI 配置能力复核  
> 适用场景：用户上传一份详细学习 Markdown，例如 Django 开发教程或知识大纲，将其转换为符合“知序”约束、可编辑、可审核、可发布的学习路线。  
> 核心原则：规则负责确定性校验，大模型负责语义理解与内容补全，人工负责最终确认；模型输出不得直接写入公开路线。

## 1. 场景结论

这个功能可以实现，而且与当前项目的路线模型、草稿编辑和管理员审核能力能够自然衔接。但不建议采用以下任一极端方式：

- 全部人工录入：质量可控，但几十天的路线需要重复填写知识点、任务、验收、代码和预期结果，成本过高。
- 仅用固定正则解析：适合项目现有的 Day 表格，不适合标题层级、章节顺序、代码块和叙述方式各不相同的普通 Markdown。
- 让大模型生成后直接入库：模型可能漏天、重复知识、捏造 API、输出不可运行代码，且长文档容易截断，不能作为可靠发布链路。

推荐采用混合管线：

```text
上传 Markdown
→ 文件与内容安全检查
→ 确定性 Markdown 解析
→ 生成来源章节索引
→ AI 按结构生成路线草稿
→ JSON Schema 与业务规则校验
→ 用户逐日预览和修改
→ 提交现有管理员审核
→ 审核通过后公开
```

对于项目维护者自己新增“Django 开发”系统路线，近期最省成本的方式仍然是先使用离线管理命令导入经过确认的结构化文件。用户上传和 BYOK 生成属于后续产品能力，应在离线方案验证数据格式和质量标准后开发。

## 2. 当前项目能够复用的能力

### 2.1 现有路线数据模型

当前 `LearningPlan` 已具备：

- 标题、副标题、简介、适合人群和主题色。
- 总天数和预计周数。
- `draft → pending → approved/rejected` 审核状态。
- 私有草稿、公开发布、Fork 和作者关系。

当前 `PlanDay` 已具备：

- Day、阶段、周次、周标题和每日标题。
- 核心知识、实践任务、验收标准和预计时间。
- `content` JSON 详细知识内容。
- `reference_answer` 综合参考实现。
- `commands` 运行或验证命令。
- 社区采纳的课程补充。

因此不需要重新设计另一套学习路线实体。新功能应生成现有 `LearningPlan + PlanDay` 能消费的数据。

### 2.2 现有导入和审核链路

项目当前只有一条版本化系统内容入口：`import_curated_roadmaps` 读取 `backend/data/system_roadmaps.v2.json`，校验后幂等写入数据库；管理员在线编辑则直接进入现有 `LearningPlan + PlanDay` 数据模型。旧的 `import_roadmap` Markdown 兼容命令已删除，不应重新作为第二条导入链路。

项目也已有用户路线链路：

```text
用户创建草稿
→ 用户编辑
→ 提交审核
→ 管理员通过或退回
→ 公开计划
```

AI 生成后的结果应进入这里的“用户草稿”，而不是新增一套发布状态机。

### 2.3 当前实现的缺口

要支持详细 Markdown 转换，还需要解决以下结构问题：

- 当前导入命令只接收已经结构化并通过目录校验的 JSON，不负责理解普通章节式 Markdown。
- 用户自定义路线序列化器目前只接收路线骨架字段，不接收完整 `content`、`reference_answer` 和 `commands`。
- `build_lesson_content` 适合作为已知知识点的默认内容模板，不能可靠代替上传文档中的详细知识和代码。
- 当前没有保存原始文档、生成任务、生成日志、校验结果和来源映射的实体；现有账号级模型配置不负责生成任务状态。
- 长文档不能安全地放入一次模型请求，需要分段、生成、校验和重试。

全局 AI 学习助手已经提供账号级多模型配置、Fernet 加密 Key、OpenAI 兼容 / Responses / Anthropic 适配器、公网 HTTPS 校验和 Redis 临时附件处理。路线生成功能必须直接复用这些能力，不再创建第二套供应商表、Key 加密逻辑或连接测试接口。

## 3. 推荐的三层数据格式

后续不要让 Markdown、模型响应和数据库字段相互直接耦合。建议固定三层格式。

### 3.1 原始来源层

保留用户上传文档及其基本信息：

- 原始文件名、大小和 SHA-256。
- Markdown 原文或私有对象存储地址。
- 上传用户、上传时间和解析版本。
- 用户填写的路线目标、学习周期、每日时间和基础水平。

原文默认私有，仅上传者和管理员可读取。路线公开不代表原始文档自动公开。

### 3.2 来源章节索引层

先用确定性 Markdown 解析器提取，而不是让模型直接阅读无边界文本：

```json
{
  "document_title": "Django 开发学习资料",
  "sections": [
    {
      "source_id": "sec-001",
      "heading_path": ["Django 基础", "请求与响应"],
      "text": "章节正文……",
      "code_blocks": [
        {"language": "python", "code": "..."}
      ],
      "links": []
    }
  ]
}
```

这一层用于控制分段、定位来源、避免章节丢失，并让每个生成学习日能够记录 `source_id`。

### 3.3 路线草稿层

定义一个带版本号的统一 JSON Schema，作为规则导入、AI 生成、人工编辑和数据库写入之间的唯一契约。

路线级字段：

```json
{
  "schema_version": 1,
  "plan": {
    "title": "Django 开发",
    "subtitle": "从请求响应到可部署项目",
    "summary": "……",
    "audience": "掌握 Python 基础的学习者",
    "target_days": 60,
    "estimated_weeks": 9
  },
  "days": []
}
```

每日字段必须覆盖当前数据库和《每日学习内容输出规范》：

```json
{
  "day_number": 1,
  "phase": "第一阶段：Django 基础",
  "week_number": 1,
  "week_title": "请求响应与项目结构",
  "title": "创建项目并理解请求链路",
  "core_knowledge": "项目结构、中间件链、URL路由、视图、响应",
  "hands_on_task": "创建最小项目并用测试客户端验证成功与404路径",
  "acceptance_criteria": [
    "正常路径返回固定JSON与200状态",
    "不存在路由返回404且测试可重复执行",
    "保存代码、测试输出和不少于100字复盘"
  ],
  "estimated_minutes": 120,
  "source_refs": ["sec-001", "sec-002"],
  "content": {
    "version": 3,
    "workflow": [],
    "knowledge_details": []
  },
  "reference_answer": "完整综合参考实现",
  "commands": ["python manage.py test"]
}
```

`knowledge_details` 中的每个知识点应继续沿用页面已支持的字段：

- `name`
- `summary`
- `basic`
- `mechanism`
- `tools`
- `pitfalls`
- `implementation_requirement`
- `reference_code`
- `language`
- `run_command`
- `expected_results`
- `mastery`

`source_refs` 可以先存在生成任务的中间 JSON 中，后期再决定是否进入 `PlanDay` 独立字段。第一版没有展示来源追踪需求时，不必立刻修改主业务模型。

## 4. 生成流程设计

### 4.1 第一步：用户配置生成目标

上传文档前后，要求用户明确：

- 路线名称和目标。
- 目标天数，例如 30、45 或 60 天。
- 每天可投入时间。
- 当前基础与期望最终作品。
- 是否允许模型补充文档没有覆盖的基础知识。
- Python、Django、数据库等版本基线。

“详细且精确的 Markdown”仍可能只是教材，不一定已经是一条学习计划。目标天数和最终产物不能完全由模型猜测。

### 4.2 第二步：确定性预处理

服务器先执行：

1. 只接受 `.md` 或明确的 `text/markdown`。
2. 校验文件大小、UTF-8 编码和空文件。
3. 清理 HTML 脚本标签等不需要内容，但保留代码块原文。
4. 提取标题层级、正文、代码块和链接。
5. 计算 Token 估算、章节数和文件哈希。
6. 检查是否已经是现有标准 Day 表格。

如果文档已经符合标准格式，应优先走规则解析，不调用模型，节省费用且结果稳定。

### 4.3 第三步：AI 生成课程骨架

模型第一次只生成路线结构，不生成全部详细代码：

- 阶段和周次。
- 连续 Day 编号。
- 每天的主题、核心知识、实践任务和验收标准。
- 每天引用的来源章节。
- 先修关系和知识覆盖矩阵。

程序随后校验天数、编号、周次、重复主题、未覆盖章节和超载学习日。骨架未通过时不进入详细生成。

### 4.4 第四步：逐日生成详细内容

按 Day 或小批次生成 `knowledge_details`、综合参考实现、测试命令和预期结果。每次请求只提供：

- 路线总目标和版本基线。
- 当前 Day 的骨架。
- 当前 Day 引用的来源章节。
- 前后少量 Day 摘要，用于避免重复和难度跳跃。
- 固定 JSON Schema 和《每日学习内容输出规范》的必要约束。

不要把整个 Markdown 和全部 60 天反复传给模型。这样可以控制上下文、成本和失败重试范围。

### 4.5 第五步：程序化质量门禁

模型返回后必须经过以下确定性检查：

#### 结构门禁

- Day 从 1 连续到目标天数，无重复和缺失。
- 每天都有阶段、周次、标题、知识、实践和至少一个验收项。
- 每个知识点的详细字段完整。
- 参考代码中不得使用 `...` 省略关键逻辑。
- 命令、语言和代码块类型一致。

#### 学习设计门禁

- 每个验收项必须可观察，不接受“了解”“熟悉”“程序不报错”。
- 每天必须包含正常路径和至少一个错误或边界路径。
- 每天必须要求保存代码、测试、日志、报告等证据。
- 单日知识点数量和预计时间不能明显失衡。
- 后续 Day 不应在前置知识出现前使用大量未解释概念。

#### Django 路线专项门禁

- 明确 Python、Django 和数据库版本。
- 代码优先使用当前版本官方 API，不能混用过期接口。
- 覆盖项目结构、URL、视图、模板或 API、模型、迁移、ORM、表单/序列化、认证权限、测试、静态文件、部署和安全配置。
- 数据库迁移、事务、权限、CSRF、生产配置等内容必须有失败路径或验证方法。
- 最终项目必须能从空目录复现，并有测试和部署说明。

#### 安全门禁

- Markdown 内容视为不可信数据，不能把其中“忽略系统要求”等文本当指令执行。
- 不执行模型生成的 shell 命令或代码。
- 不让模型直接连接数据库、文件系统或管理接口。
- 检查是否包含密钥、Token、真实密码或个人信息。

### 4.6 第六步：用户预览与人工修改

生成结果先成为“导入草稿”，页面应提供：

- 路线总览和知识覆盖矩阵。
- 每天的来源章节、生成状态和校验状态。
- 缺失、重复、超时和版本冲突提示。
- 单日重新生成，而不是整条路线重做。
- 用户手动编辑任何字段。
- 生成前后差异预览。

只有用户确认后，才把完整结果写入现有私有 `LearningPlan` 草稿。

### 4.7 第七步：复用现有审核发布

写入路线草稿后继续使用现有流程：

```text
draft
→ 用户预览并修改
→ pending
→ 管理员逐日检查
→ approved / rejected
```

管理员页面后期应额外显示：

- 生成方式：规则导入、AI 辅助或纯人工。
- 模型和生成时间，但不显示 API Key。
- 原始文档哈希、来源覆盖率和校验报告。
- 用户是否允许模型补充来源外内容。
- 随机抽查的参考代码与命令。

## 5. 复用现有账号级模型配置

### 5.1 第一版建议

第一版不再让用户重复填写一套供应商信息。页面直接选择当前账号已有的 `AIProviderCredential`，也可沿用全局助手的临时配置进行单次同步生成。

- 已保存 Key 继续只以 Fernet 密文存在 MySQL，由服务端在请求供应商前短暂解密；接口、日志、任务结果和管理员页面都不能返回明文。
- 生成任务保存凭据 ID 以及创建时的协议、模型和规范化地址快照，不复制 Key 密文。任务继续执行前验证凭据仍属于当前用户且未被删除；公开配置发生变化时要求用户确认，不静默切换供应商。
- 临时 Key 只适用于当前请求内可完成的同步步骤，不写 MySQL、Redis、Cookie 或浏览器持久存储。需要后台续跑的任务必须选择已保存配置。
- 日志只记录供应商、模型、Token 用量、耗时和错误类别；页面明确说明 Markdown 会发送给所选第三方服务商。
- 仍由现有 URL 安全校验拒绝本机、内网、保留地址、内嵌凭据和重定向，不能为路线生成另开绕过入口。

### 5.2 后续可选能力

只有真实生成量证明同步调用长期占满 Web Worker 时，才增加后台 Worker。届时仍复用同一凭据表和加密主密钥，不增加路线生成专用 Key 表；队列消息只传任务 ID 与凭据 ID。

## 6. 建议新增的数据实体

第一版正式产品能力可新增以下最小实体，不把生成状态塞入 `LearningPlan`：

### 6.1 `RoadmapSource`

- `user`
- `filename`
- `file_hash`
- `content` 或私有文件地址
- `size`
- `parse_status`
- `created_at`

### 6.2 `RoadmapGeneration`

- `user`
- `source`
- `status`：uploaded / parsing / outlining / generating / validating / ready / failed / imported
- `provider`
- `model`
- `credential`，可空且只能关联任务所有者的现有 AI 配置
- `schema_version`
- `target_days`
- `preferences` JSON
- `outline` JSON
- `result` JSON
- `validation_report` JSON
- `current_day`
- `error_code` 和脱敏错误摘要
- Token 用量、估算费用和时间字段
- `imported_plan`，成功导入后关联现有 `LearningPlan`

暂时不需要为每一次模型请求建立复杂表；调试信息可以保留在脱敏结构化日志中。只有真实运营证明需要精细计费和重放时，再增加请求明细表。

## 7. API 与页面草案

建议新增入口：`/plans/import`。

用户流程：

1. 上传 Markdown。
2. 填写目标天数、每天时长、基础和版本要求。
3. 选择“规则解析”或“AI 辅助”；系统检测到标准格式时默认规则解析。
4. 选择账号已有模型配置并测试连接；单次同步生成可选择临时配置。
5. 查看费用和 Token 预估，确认生成。
6. 查看任务进度与失败原因。
7. 预览路线骨架和覆盖矩阵。
8. 逐日查看、编辑或重新生成。
9. 导入为我的路线草稿。
10. 使用现有路线详情页提交管理员审核。

接口可以保持资源化：

- `POST /api/roadmap-sources/`：上传和解析 Markdown。
- `POST /api/roadmap-generations/`：创建生成任务。
- `GET /api/roadmap-generations/{id}/`：查看进度和结果。
- `POST /api/roadmap-generations/{id}/regenerate-day/`：只重做一天。
- `PATCH /api/roadmap-generations/{id}/`：修改草稿结构。
- `POST /api/roadmap-generations/{id}/import/`：原子写入现有路线草稿。
- `DELETE /api/roadmap-generations/{id}/`：删除来源与生成结果。

第一版不需要 WebSocket。任务进度可以每 2～5 秒轮询，避免增加实时通信复杂度。

## 8. 失败处理与幂等

- 上传文件以用户和文件哈希识别重复来源，但允许用户基于同一来源建立不同目标天数的生成任务。
- 每个生成任务拥有幂等键；重复点击开始不能产生两条并行任务。
- 每个 Day 单独保存生成状态，失败后从失败 Day 继续。
- 模型返回非 JSON 时先执行有限次数的结构修复，仍失败则显示原因为“结构不合法”，不写主业务表。
- 导入操作使用数据库事务；任一 Day 校验失败时整条路线不写入。
- 同一生成任务只能导入一次，重复请求返回已经创建的路线。
- 用户删除生成任务时，应同时删除原始 Markdown；已经导入的路线不自动删除。

## 9. 成本与性能控制

长文档和 60 天详细课程会产生明显模型费用，页面必须在生成前给出估算：

- 文档输入 Token。
- 骨架生成 Token。
- 每日详细内容预计 Token。
- 预计总费用区间。
- 已完成和剩余用量。

控制方式：

- 已符合规范的段落直接复用，减少模型重写。
- 骨架与详细内容分阶段生成。
- 只向模型提供当前 Day 的来源章节。
- 单日失败只重试当前 Day。
- 保存文档章节摘要，避免重复摘要。
- 限制单文件大小、最大天数、并发任务数和每日生成次数。

公益站不能替使用 BYOK 的用户承担无限生成请求，也不能让错误任务持续消耗用户额度。

## 10. Django 开发路线的首次落地建议

这条路线可以作为该能力的验证样本，推荐顺序如下：

### 10.1 先定义目标

建议先人工确定：

- Python 3.12。
- Django 5.2 LTS 或项目最终选定版本。
- MySQL 8。
- 目标周期，例如 60 天。
- 最终产物：一个具有认证、权限、测试、MySQL、静态文件和部署能力的完整项目。

版本属于易变信息，真正生成时需要基于官方文档核对，而不能完全相信上传材料或模型记忆。

### 10.2 用规则和 AI 生成结构化草稿

1. 解析 Django Markdown 章节。
2. AI 只生成 60 天骨架和章节覆盖矩阵。
3. 人工确认主题顺序和每日负载。
4. 逐日生成详细知识、最小实验、综合任务和测试。
5. 对关键阶段抽样实际运行参考代码。
6. 导入私有草稿并通过网站管理员审核发布。

### 10.3 不建议人工逐字段塞数据库

不应在 MySQL 中直接执行插入，也不应长期在 `curated_roadmaps.py` 手工维护几十天的大量正文。更合适的临时形式是：

- 把确认后的路线保存为版本控制中的 JSON 或 YAML。
- 使用幂等 Django 管理命令校验并导入。
- 正式生成产品完成后，同一份结构化文件仍可通过统一导入服务进入草稿。

这样既保留人工审核质量，也避免数据库手工操作和不可追踪修改。

## 11. 分阶段开发顺序

### 阶段 A：统一结构化导入（建议先做）

- 定义 `roadmap.schema.v1.json`。
- 把现有规则解析和 curated 路线统一转换为该结构。
- 增加 JSON/YAML 校验命令和幂等草稿导入命令。
- 用 Django 开发路线作为首个完整样本。
- 为连续 Day、必填字段、验收可执行性和事务回滚增加测试。

完成标准：不依赖 AI，也能把一份合法结构化路线稳定导入为私有草稿。

### 阶段 B：Markdown 上传与规则解析

- 增加私有 Markdown 上传、来源章节索引和预览。
- 标准 Day 表格直接转换，不调用 AI。
- 用户确认后进入统一草稿格式。

完成标准：结构规范的 Markdown 可以在网页中无模型、低成本导入。

### 阶段 C：AI 辅助骨架生成

- 支持临时 BYOK。
- 生成阶段、周次、Day 骨架和来源覆盖矩阵。
- 增加结构校验、费用预估、失败恢复和用户编辑。

完成标准：不同章节结构的 Markdown 能生成连续、可修改且有来源映射的路线骨架。

### 阶段 D：逐日详细内容生成

- 分 Day 生成知识详情、参考实现、命令和结果。
- 支持单日重新生成。
- 增加 Django 等主题专项门禁和抽样运行验证。
- 导入后复用现有管理员审核。

完成标准：生成内容满足《每日学习内容输出规范》，任何不合格 Day 都不能进入可提交草稿。

### 阶段 E：规模化与运营安全

- Redis/Worker 异步生成和短期加密凭据。
- 任务并发、配额、限速、成本统计和告警。
- 原文删除、数据保留、模型服务商隐私说明。
- 生成质量指标和管理员抽查工具。

没有真实生成量之前，不提前引入复杂工作流框架或向量数据库。

## 12. 测试与验收清单

### 12.1 解析与结构

- 标准 Day 表格不调用模型并得到稳定结果。
- 普通标题式 Markdown 正确提取标题路径和代码块。
- 空文件、乱码、超限文件和伪装扩展名被拒绝。
- 1 天、60 天和 365 天边界正确；超过 365 天被拒绝。
- Day 编号缺失、重复或乱序不能导入。

### 12.2 模型输出

- 非 JSON、截断 JSON、缺字段和错误类型可明确报告。
- 模型拒绝、限流、超时和余额不足不会留下半成品路线。
- 单日重试不改变已经由用户确认的其他 Day。
- 文档中的提示注入文本不能改变系统 Schema 和发布规则。
- 模型生成的代码不会在网站服务器上自动执行。

### 12.3 权限与隐私

- 用户只能读取和删除自己的来源及任务。
- 普通用户不能查看他人 Markdown、模型结果或 Key。
- API Key 明文不进入数据库、响应、日志和错误监控；保存模式只复用现有 Fernet 密文。
- 管理员审核路线时不获得用户 API Key。
- 删除生成任务会删除原文和未导入结果。

### 12.4 导入与发布

- 导入失败时 `LearningPlan` 和全部 `PlanDay` 一起回滚。
- 重复导入同一任务不会创建重复路线。
- AI 路线默认是私有草稿。
- 草稿仍需用户确认和管理员审核才能公开。
- 已开始学习或已发布路线继续遵守当前编辑限制。

### 12.5 内容质量

- 每天都有可运行实验或与任务类型对应的真实产物。
- 每天都有正常路径、错误路径、命令和预期结果。
- 验收项不是“了解、熟悉、没有报错”等不可验证表述。
- 参考实现不省略核心逻辑。
- Django 路线中的关键代码在指定版本环境抽样运行通过。
- 原始文档主要章节均被覆盖或明确列入“未采用章节”。

## 13. 风险与边界

### 13.1 AI 不能保证知识正确

模型更适合做内容拆分、结构转换和初稿补全，不能替代官方版本核对、代码运行和管理员审核。页面必须把“AI 生成”标记为草稿来源，而不是质量认证。

### 13.2 上传材料可能存在版权问题

用户应确认拥有材料的处理权限。公开路线应优先发布重新组织的知识目标、实践任务和少量必要示例，不能把受保护教程正文整体改写后公开。原始文档默认私有。

### 13.3 API Key 和文档属于敏感数据

BYOK 会使服务器接触用户密钥和学习资料。没有日志脱敏、HTTPS、限速、删除机制和隐私说明前，不应上线该能力。

### 13.4 模型服务商差异

不同服务商的结构化输出、上下文长度和错误格式不同。业务层应依赖统一的内部生成接口和 JSON Schema，不应让页面或数据库直接依赖某一家 SDK 返回结构。

## 14. 最终建议

针对当前项目，推荐决策是：

1. 不人工向 MySQL 塞路线数据。
2. 不让大模型直接写 `LearningPlan` 和 `PlanDay`。
3. 先建立统一、可版本化、可校验的路线 JSON Schema。
4. 对规范 Markdown 优先使用规则解析，只有非标准语义转换和内容补全才调用模型。
5. AI 结果先进入独立生成草稿，再由用户确认后导入现有路线草稿。
6. 继续复用当前管理员审核与发布状态机。
7. 直接复用现有账号级模型配置和临时模式，不建设第二套 BYOK 存储，并继续限制服务商地址。
8. 用“Django 开发 60 天路线”作为离线样本，先验证 Schema、导入和质量门禁，再开发网页生成能力。

这条路线既能明显降低人工录入成本，也不会把课程质量、用户密钥和公开发布安全完全交给模型。
